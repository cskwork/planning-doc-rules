# 기획서 작성을 위한 10가지 원칙

[English](README.md) | **한국어**

서비스 기획, 소프트웨어 기획, 사업 기획, 전략 기획 문서를 함께 쓰는 AI 에이전트(Claude Code, Codex CLI, Gemini CLI, OpenCode, Cursor 등)를 위한 최소 시스템 프롬프트입니다.

두 개의 파일. 열 개의 원칙. 군더더기 없음.

랜딩 페이지: **https://cskwork.github.io/planning-doc-rules/**

## 왜 필요한가

좋은 기획서는 아이디어 설명서가 아니라 **의사결정 문서**입니다. 다음 한 줄이 모든 챕터를 관통해야 합니다.

> 왜 해야 하는가 → 어떤 문제를 해결하는가 → 누구를 위한 것인가 → 무엇을 만들 것인가 → 어떻게 실행하는가 → 어떻게 검증하는가

대부분의 기획서 템플릿이 실패하는 이유는 챕터만 나열할 뿐, 위 한 줄로 묶이지 않기 때문입니다. 승인자는 비용 대비 효과를 찾지 못하고, 개발자는 예외 케이스를 못 찾고, QA는 수용 기준을 못 찾습니다. 이 열 가지 원칙은 모든 챕터가 같은 실 하나로 꿰이도록 강제합니다.

## 설치

에이전트가 읽는 파일을 홈 디렉토리 또는 프로젝트 루트에 넣으면 됩니다.

| 도구 | 파일 |
|------|------|
| Claude Code | `~/.claude/CLAUDE.md` 또는 `<repo>/CLAUDE.md` |
| OpenAI Codex CLI | `~/.codex/AGENTS.md` |
| Google Gemini CLI | `~/.gemini/AGENTS.md` |
| OpenCode | `~/.config/opencode/AGENTS.md` |
| Cursor / Windsurf / 기타 | `<repo>/AGENTS.md` |

### 한 줄 설치

```bash
curl -fsSL https://raw.githubusercontent.com/cskwork/planning-doc-rules/main/AGENTS.md -o ~/.codex/AGENTS.md
curl -fsSL https://raw.githubusercontent.com/cskwork/planning-doc-rules/main/CLAUDE.md -o ~/.claude/CLAUDE.md
```

### 여러 CLI에서 단일 출처로 유지

```bash
git clone https://github.com/cskwork/planning-doc-rules.git ~/planning-doc-rules

ln -sf ~/planning-doc-rules/CLAUDE.md   ~/.claude/CLAUDE.md
ln -sf ~/planning-doc-rules/AGENTS.md   ~/.codex/AGENTS.md
ln -sf ~/planning-doc-rules/AGENTS.md   ~/.gemini/AGENTS.md
ln -sf ~/planning-doc-rules/AGENTS.md   ~/.config/opencode/AGENTS.md
```

## 열 가지 원칙

1. **Why를 먼저 고정하라.** 무엇을 만들 것인가가 아니라, 왜 지금 해야 하는가, 해결하지 않으면 무엇이 깨지는가, 어떤 조직·사용자·시장 니즈에 답하는가를 먼저 쓴다.
2. **문제를 As-Is / To-Be 격차로 정의하라.** 불만이나 아이디어가 아니라 현재 상태, 목표 상태, 그 차이, 핵심 원인, 우선 해결 순서로 쓴다.
3. **독자의 우려를 목차로 바꿔라.** 작성자가 하고 싶은 말이 아니라 승인자·개발자·디자이너·운영자·투자자가 걱정하는 순서대로 챕터를 배치한다.
4. **리서치로 주장과 의견을 분리하라.** 데스크 리서치, 경쟁 분석, 사용자 인터뷰, 로그, 리뷰, VOC에서 근거를 가져온다. 검증 안 된 부분은 *가정* 또는 *추가 검증 필요*로 명확히 표시한다.
5. **사용자 시나리오에서 요구사항을 도출하라.** 페르소나, 상황, 목표, 여정이 먼저고, 기능은 그 행동에서 떨어져 나온다.
6. **요구사항을 모호하지 않게 명세하라.** ID, 명, 목적, 상세, 사용자, 입력값, 처리 조건, 출력값, 예외, 우선순위, 수용 기준까지 적어 개발·QA·운영이 같은 기준으로 판단할 수 있게 한다.
7. **IA → Flow → Wireframe → Spec을 연결하라.** 모든 화면은 어떤 요구사항을 충족하는지, 모든 요구사항은 어느 화면에 떨어지는지 추적 가능해야 한다.
8. **정책과 예외를 먼저 정의하라.** 정상 플로우가 아니라 권한, 상태값, 데이터 보관·삭제, 알림, 승인·반려, 오류, 운영자 개입 케이스를 스펙 확정 전에 박는다.
9. **실행 가능성을 숫자와 계획으로 증명하라.** 범위, 제외 범위, 우선순위, 일정, 인력, 리소스, 의존성, 리스크, 대안, 단계별 실행 계획을 모두 적는다.
10. **검증·론칭·운영까지 닫아라.** 개발 완료가 끝이 아니다. QA 시나리오, 테스트케이스, 론칭 계획, 운영 매뉴얼, CS 대응, KPI, 사후 고도화 사이클까지 포함한다.

원칙별 출력 구조, 자가 진단 체크리스트, 100점 채점 기준의 전체 내용은 [CLAUDE.md](CLAUDE.md) / [AGENTS.md](AGENTS.md)에 있습니다.

## 표준 목차

이 원칙대로 작성된 기획서는 보통 다음 순서를 따릅니다. **순서 자체가 규칙(원칙 3)** 입니다 — 각 챕터는 그 시점에 독자가 갖는 특정 우려에 답합니다.

1. 한 줄 결론
2. Executive Summary
3. 배경과 문제
4. As-Is / To-Be
5. 목표와 성공 지표
6. 사용자 / 시장 / 경쟁 리서치
7. 핵심 인사이트
8. 해결 방향과 대안 비교
9. 범위와 제외 범위
10. 사용자 시나리오
11. 요구사항(기능 + 비기능)
12. IA / 메뉴 구조
13. 주요 Flow
14. 와이어프레임(이미지 없으면 텍스트 트리)
15. 정책 / 권한 / 예외 케이스
16. 일정 / 리소스 / 리스크
17. QA·검증 계획
18. 론칭·운영·KPI 계획

## 설계 노트

- **두 파일, 동일 내용.** `AGENTS.md`는 크로스 툴 표준, `CLAUDE.md`는 Claude Code가 자동으로 로드하는 파일. 둘 다 두면 툴별 분기 없음.
- **선언형, 묘사형이 아님.** 각 원칙은 “X를 먼저 박아라. Y로 시작하지 마라.” 형태의 지시문이지 가치 진술이 아니다.
- **Why 기반이지 템플릿 기반이 아님.** 구조는 Why에 봉사한다. 의사결정 가치가 없는 챕터는 현재 문서에서 뺀다.
- **자가 진단이 강제됨.** 에이전트는 초안을 완성했다고 주장하기 전 체크리스트와 100점 채점을 반드시 수행한다. 미완성 기획서가 통과되는 가장 흔한 원인을 막기 위해서다.
- **행동 vs 커뮤니케이션 분리.** 열 가지 원칙은 *문서에 무엇을 담을지*를, *Response & Documentation Style*은 *작성 중 에이전트가 어떻게 말할지*를 규정한다.

## 커스터마이징

Fork 하라. *Repository Rules* 섹션부터 손대라 — 팀 색이 가장 짙다. 열 가지 원칙은 기존 원칙이 못 잡는 실제 실패 모드를 발견했을 때만 손대라.

원칙을 추가한다면:

- 한 문장으로 표현될 것.
- 출시된 기획서에서 실제로 본 실패 모드와 연결될 것.
- 기존 원칙과 중복되지 않을 것.

원칙이 ~20개를 넘기면 그건 시스템 프롬프트가 아니라 위키다.

이 원칙은 다음 자료에서 반복적으로 등장하는 패턴을 정리한 것입니다.

- 박신영, 『기획의 정석』, 세종서적 — 3WR, 5Why, 현상 분해와 그룹핑, “상대방의 두려움을 없애는 기획서” 관점.
- 조이, 『서비스를 성공시키는 기획자의 비법 노트』, BJ퍼블릭 — 리서치 → 문제 정의 → 요구사항 수집 → 페르소나 → 유저 시나리오 → IA → 메뉴 트리 → 플로우차트 → 와이어프레임 → 프로토타이핑 → 기능 요구사항 명세서 → 화면 ID → 정책서 → QA → 론칭 → 운영 → 성과 측정으로 이어지는 서비스 기획 전 과정.
- 이경희, 『서비스 기획 용어사전』, 연플 — 요구사항 정의서, 플로우차트, IA, 와이어프레임, 정책, 분기·예외처리, 화면설계서, QA·테스트케이스, 유저스토리, WBS, 스프린트 등 실무 공용 언어.
- Rational 기술팀, 『똑똑한 소프트웨어 개발을 위한 실용 가이드』, 한국아이시스 — 요구사항 관리, 분석·설계·모델링, 요구사항-개발-테스트 추적성, 협업, 품질 관리.
- 정보통신산업진흥원(NIPA), 공공 SW 사업 요구사항 상세화 가이드 — RFP 수준 요구사항 명세의 제도적 기준.
